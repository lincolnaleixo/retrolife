# Save states

Save states capture a running Super Nintendo session so it can be restored later. They are separate from the game's own battery-backed save file. Keep using the game's normal save feature as well.

## Controls

Open **Saves** from the gameplay header, **Save & load states** from the pause menu, or the save-state section in Game settings. The browser shows six manual slots, a Quick slot and a Recovery slot. Each saved entry includes its capture and time information when available. Empty or incompatible slots cannot be loaded.

- **F5** saves to the Quick slot.
- **F6** opens the save-state browser.
- **F7** opens the Quick slot's load confirmation.

Replacing an occupied slot or loading a state requires confirmation. Recovery is reserved for the position immediately before a load and is available to restore from the browser. It cannot be overwritten through an ordinary manual save action.

## Pause and input behavior

Opening the browser pauses the emulator and releases held game inputs. Browsing, confirming or waiting for a save/load operation cannot advance the game or send controls to it. Closing the browser restores its previous playing or paused state. A button held while closing must be released before it can control the game again.

Errors remain visible with the game paused so the operation can be retried without losing track of its outcome. Closing or exiting is blocked while the backend is still confirming a pending write or restore. A load replaces the displayed frame and clears queued audio before playback continues. A result belonging to an earlier session must never update a newly started game.

## Compatibility and achievements

A save state is checked against the ROM bytes, core code/data, core options and platform. Normal macOS re-signing is excluded from the compatibility fingerprint for supported Mach-O layouts; executable changes still invalidate it. It is not a portable exchange format across games or arbitrary core builds. The browser disables unavailable or incompatible entries. Games without save-state support retain ordinary pause and exit controls.

Restoring a state is a discontinuity for automatic achievements. Previously earned rewards remain durable, while pending gameplay observations must be reset so loading a scene cannot itself award a quest.

## Storage and recovery

State files live beside the existing per-game save directory under `states/<ROM SHA-256>/slot-<number>.rts`. A state stores bounded core data and a raw screenshot, together with its identity metadata and checksum. Writes replace the selected slot atomically; they do not overwrite `battery.srm`.

Loading first validates the target and writes the current position to Recovery. If either step fails, it does not load the target. If the core rejects restoration after mutation, the backend attempts rollback. A failed rollback makes the session unsafe: resuming or creating another state is rejected, and exit releases the core without overwriting the existing battery save. The Recovery file remains on disk.

## Verification

The frontend smoke suite uses synthetic frames and a fake asynchronous backend. It exercises pause ownership, input isolation, slot confirmations, failed operations and stale completions without reading a ROM, save file, account or real user preferences. The native smoke suite imports only the exact original ROM generated by `scripts/make-test-rom.py` into its own temporary library. It exercises real core serialization, preview delivery, confirmation, Recovery, a restored frame while paused, and a fresh bridge reading the durable slots. Backend tests separately verify serialization failures and storage validation; none of these fixtures replace testing commercial game compatibility.
